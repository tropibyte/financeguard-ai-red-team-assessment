# Supply Chain Vulnerability Analysis

Source artifacts: `06_trivy_report.json` (Trivy scan of the built image,
`offensive-ai-course`, Debian 13.4 base) and the project `Dockerfile`. Generated by
`attacks/05_supply_chain_analysis.py`.

## Vulnerability Summary

| Severity | Count |
|----------|-------|
| CRITICAL | 0 |
| HIGH | 34 |
| MEDIUM | 160 |
| LOW | 601 |
| UNKNOWN | 9 |
| **Total** | **804** |

The scan covers two layers: **OS packages** (Debian, 801 findings) and **Python
packages** (lang-pkgs, 3 findings). There are no CRITICAL CVEs, but 34 HIGH warrant
attention. A key nuance for triage: **31 of the 34 HIGH are OS-layer CVEs with no
fix available**, and **30 of those are `linux-libc-dev`** — kernel *header* packages
that ship dev headers, not a runtime library the Flask app loads, so they are not
directly exploitable from the running container. The genuinely actionable HIGHs are
the **3 Python-package CVEs (all fixable today)** plus one `libexpat1` XML CVE.

## Python-Specific Vulnerabilities

All three Python HIGH findings have fixes and should be patched immediately — these
are dependencies the application actually installs and can control via
`requirements.txt`:

- **wheel 0.45.1 → 0.46.2** (CVE-2026-24049): a malicious `.whl` can trigger
  privilege escalation or code execution during install. Directly relevant to a
  build pipeline that runs `pip install`.
- **jaraco.context 5.3.0 → 6.1.0** (CVE-2026-23949): path traversal when handling a
  crafted tar archive.

Note these are *build/packaging* dependencies pulled in transitively (via
setuptools/pip tooling), which is exactly the class of package a supply-chain
attacker targets — they run with the builder's privileges and are easy to overlook.

## Dockerfile Issues

Six issues were identified by `analyze_dockerfile()`:

### 1. Container runs as root (no USER directive) — HIGH

**Risk:** No `USER` instruction, so the Flask app (and any exploit against it — e.g.
a prompt-injection that reaches code execution, or a malicious dependency) runs as
root (UID 0) inside the container. A container escape then starts from root.
**Fix:** Add a non-root user and switch to it before `CMD`:
`RUN useradd -m appuser && chown -R appuser /app` then `USER appuser`.

### 2. Unpinned base image (no SHA256 digest) — MEDIUM

**Risk:** `FROM python:3.11-slim` uses a mutable tag. The image can change between
builds (non-reproducible) and the tag could be repointed at a malicious image.
**Fix:** Pin by digest: `FROM python:3.11-slim@sha256:<digest>`.

### 3. `COPY . /app` copies the entire build context — MEDIUM

**Risk:** Bakes the whole context into the image — including `rag_chatbot/.env`
(which holds the OpenAI/Vocareum API key), the `.git` history, model checkpoints,
and any local artifacts. Anyone who pulls the image gets the secrets.
**Fix:** Copy only what is needed and add a strict `.dockerignore` covering `.env`,
`.git`, `__pycache__`, `*.pt`, and test data.

### 4. No HEALTHCHECK defined — LOW

**Risk:** Orchestrators cannot distinguish a wedged/crashed container from a healthy
one and keep routing traffic to a dead app.
**Fix:** `HEALTHCHECK CMD curl -f http://localhost:5001/health || exit 1` (the app
already exposes `/health`).

### 5. Build tools left in the production image (build-essential, gcc) — MEDIUM

**Risk:** Compilers/toolchains remain in the runtime image, enlarging the attack
surface and handing an attacker the tools to compile further exploits in place.
**Fix:** Use a multi-stage build — compile in a builder stage, copy only runtime
artifacts into a clean final image.

### 6. Unnecessary tools in image (curl, git) — LOW

**Risk:** `curl` and `git` are not needed at runtime but give an attacker ready-made
means to pull payloads and move laterally after a compromise.
**Fix:** Remove runtime tools not required by the app, or install them only in a
builder stage.

## AI Pipeline Risk Assessment

Supply-chain weaknesses are especially damaging for an AI system because the model
and its data *are* the product:

- **Model integrity.** The pre-trained checkpoint (`receipt_cnn_clean.pt`) and the
  FAISS index are copied into the image with **no integrity verification** (no hash,
  no signature). A tampered checkpoint (e.g., a backdoored classifier) or a poisoned
  index would ship silently — the same integrity gap the label-flip poisoning attack
  (VUL-002) exploits from the data side.
- **Dependency security.** `requirements.txt` pins versions but **not hashes**, so a
  compromised or typo-squatted package (dependency confusion) could be substituted.
  The fixable `wheel`/`jaraco.context` CVEs show packaging tooling is already a live
  risk. `pip install --require-hashes` closes this.
- **Runtime privilege.** Because the container runs as **root**, any path from the
  externally-reachable `/chat` endpoint to code execution — including via a
  successful prompt injection — yields root, turning an application-layer AI flaw
  into full host-level compromise.
- **Secret exposure.** `COPY .` embeds the API key (`.env`) into the image; a leaked
  image leaks the credential and its budget.

## Remediation Priority

| Priority | Action |
|----------|--------|
| 1 | Run the container as a **non-root user** and add a `.dockerignore` so `.env`/secrets and `.git` are never baked into the image (`COPY .` fix). |
| 2 | **Patch the 3 fixable Python HIGH CVEs** — bump `wheel` → 0.46.2 and `jaraco.context` → 6.1.0 — and adopt `pip install --require-hashes` to block dependency substitution. |
| 3 | Harden the build: **pin the base image by SHA256 digest**, move to a **multi-stage build** (drop build-essential/gcc/curl/git from the final image), and add a **HEALTHCHECK**; add integrity checks (hash/signature) for the model checkpoint and FAISS index. |
